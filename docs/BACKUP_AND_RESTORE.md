# CareFlow Hub — Full-system backup and recovery

## Scope and safety

The full-system backup is generated by the scheduled GitHub Actions worker, not by the browser. It creates an encrypted archive containing:

- A full custom-format PostgreSQL logical dump of the database, including application schemas plus Supabase Auth and Storage metadata. The worker explicitly checks for the Auth users/identities, Storage buckets/objects and migration ledger tables.
- Every Storage bucket configuration and every object file, with per-object SHA-256 checksums.
- The repository's immutable `supabase/` migrations, Edge Function source, configuration and application source snapshot at the backup commit.
- An internal manifest with project ref, backup ID, timestamp, component counts and checksums.

The archive is encrypted client-side using `age` before it leaves the runner. The archive is stored in a **private Cloudflare R2 bucket**. Only a small, non-sensitive manifest is stored separately so the application can list verified backups. GitHub Actions artifacts are not used as the backup destination.

External secrets such as Supabase service-role/secret keys, database connection passwords, R2 credentials, GitHub tokens, Edge Function secrets and the age private identity are never written into the backup archive or repository. However, the database snapshot includes database-resident settings and application records. CareFlow currently stores SMTP settings in the `system_settings` table, so any SMTP password saved there is included inside the encrypted database backup. Treat the archive as highly confidential, protect the offline age identity, and rotate database-resident credentials if an archive or recovery key is exposed. External environment/function secrets must be re-entered during recovery.

Supabase database snapshots do not include the actual Storage object bytes; this worker exports every Storage object separately. The Supabase CLI `db dump` command excludes managed `auth` and `storage` schemas by default, so this worker intentionally uses raw PostgreSQL `pg_dump` and verifies that Auth, Storage metadata and migration-history tables are present.

## How to operate

1. The workflow runs daily at 02:00 UTC.
2. An authorised system administrator can request an on-demand run from Settings → Backup. Requests are rate-limited to one per administrator per 10 minutes.
3. The worker uses a PostgreSQL client matching the server major version to create a portable custom-format `pg_dump` of the full database. It verifies that the archive contains the required `auth.users`, `auth.identities`, `storage.buckets`, `storage.objects` and `supabase_migrations.schema_migrations` tables, exports every Storage object, snapshots the source commit, creates the package, encrypts it, uploads it to R2, downloads it again and compares SHA-256. This logical-dump path does not depend on the Supabase plan's daily backup availability.
4. The plaintext manifest is uploaded **last**. Its presence with `verification=sha256-verified` is the commit marker that the backup completed successfully.
5. The Backup Center only lists manifests that pass project-ref and verification checks. It issues a 60-second signed download URL on demand.

A workflow failure, missing secret, API error, incomplete Storage listing, upload error, or checksum mismatch must fail the job and must not publish a successful manifest.

## Recovery procedure

**Do not restore over the live production project as the first recovery action.** Prefer a replacement Supabase project in the correct region/plan, and verify the replacement before switching the app over.

1. Create or identify a replacement Supabase project. Record its project ref and database password. Confirm PostgreSQL major-version compatibility with the source backup.
2. Download the encrypted backup from Settings → Backup. Record the `encrypted_sha256` shown in the verified manifest.
3. On a trusted recovery workstation, install `age`, `tar` and the Node.js runtime. Keep the age private identity in a protected file; never upload it to GitHub, Supabase, the app or R2.
4. Run the checksum-verified decrypt and extraction step:
   ```bash
   export BACKUP_AGE_IDENTITY_FILE=/secure/offline/careflow-age-identity.txt
   export BACKUP_EXPECTED_SHA256=<manifest-encrypted-sha256>
   bash scripts/restore-system-backup.sh careflow-system-backup.tar.gz.age
   ```
   The script verifies the encrypted package checksum, decrypts it, rejects unsafe paths, symlinks, hardlinks and special files before extraction, then validates the database dump, source snapshot and every Storage object checksum.
5. Create a replacement Supabase project in the same region and with the same PostgreSQL major version (the backup worker supports PostgreSQL 14–19). Obtain its **Session Pooler** connection URI (port 5432) from the Supabase Connect dialog. Restore the database into that replacement project:
   ```bash
   export RESTORE_TARGET_PROJECT_REF=<new-project-ref>
   export RESTORE_TARGET_DB_URL='postgresql://postgres.<new-project-ref>:<password>@<session-pooler-host>:5432/postgres?sslmode=require'
   export RESTORE_CONFIRMATION="RESTORE-DATABASE-TO:${RESTORE_TARGET_PROJECT_REF}"
   # Only if you reviewed the manifest and intentionally want public buckets:
   # export RESTORE_ALLOW_PUBLIC_BUCKETS=YES
   bash scripts/restore-database.sh <verified-extracted-directory>
   ```
   The script verifies the target PostgreSQL major version, requires explicit target confirmation, refuses to overwrite the source project by default, blocks the restore if public buckets are present without explicit approval, and restores the custom-format dump transactionally. This is destructive to the target database; use a new project first.
6. After the target database is restored and the target project is healthy, restore the Storage buckets and objects:
   ```bash
   export RESTORE_TARGET_SUPABASE_URL=https://<target-ref>.supabase.co
   export RESTORE_TARGET_PROJECT_REF=<target-ref>
   export RESTORE_TARGET_SERVICE_ROLE_KEY=<target-service-role-key>
   export RESTORE_CONFIRMATION="RESTORE-STORAGE-TO:${RESTORE_TARGET_PROJECT_REF}"
   node scripts/restore-storage.mjs <verified-extracted-directory>
   ```
   The script creates or updates bucket configuration, uploads objects, and downloads each uploaded object again to verify SHA-256. If the source backup contains public buckets, review them first and explicitly set `RESTORE_ALLOW_PUBLIC_BUCKETS=YES` only when public access is intended; otherwise the restore script refuses to make any bucket public.
7. Deploy the exact source commit recorded in the manifest. Re-deploy Edge Functions and configure all secrets independently; secret values are intentionally not backed up.
8. Validate Auth login, role assignments, RLS, claims, pre-authorizations, settlements, ledger balances, reports, Storage downloads, Edge Functions, email configuration and audit logging.
9. Only after successful acceptance should DNS/frontend environment be switched to the replacement project. Keep the old project untouched until sign-off.

## Recovery limitations that must be tested before production certification

- The custom-format PostgreSQL dump and restore command must be verified with a real CareFlow backup and a disposable replacement Supabase project. This repository does not claim a successful end-to-end restore until that test passes.
- The worker requires a PostgreSQL session-pooler connection URI and a database role with read access to the required schemas. It fails closed if the required Auth, Storage metadata or migration-ledger tables are missing.
- Supabase platform database backups and PITR do not include Storage objects; this worker includes Storage separately.
- Platform Auth/provider settings, OAuth client secrets, SMTP transport secrets, Edge Function secrets, JWT/API keys, custom domains and third-party integrations must be reconfigured or rotated. The PostgreSQL dump includes `auth.users` and `auth.identities`, including password hashes, but it does not include cluster-wide role definitions/passwords or project-level provider configuration.
- R2 is off-site from the Supabase project. It must remain private, have independent access controls, and retain the age private key securely.
- The first successful scheduled run and a complete restore rehearsal are mandatory before the UI may be treated as production-ready.
